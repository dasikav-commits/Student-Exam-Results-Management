# Paper Moderation integration — first PR

## Starting point and decisions

- **Results rollback point:** `Dasika` at [`725785c7ab647beab5a41af8aa5c594c48a40d6b`](https://github.com/dasikav-commits/Student-Exam-Results-Management/commit/725785c7ab647beab5a41af8aa5c594c48a40d6b), after results PR #14. It already contains CA registers and best-N scoring, final-paper blueprints and first marking, Second Examiner correction/reconciliation, and HOD result sheets. See [the results workflow notes](second-examiner-workflow.md). This PR does not replace those workflows or their database columns.
- **Moderation reference:** [Paper-Moderation-System `Dasika` at `c55687a`](https://github.com/dasikav-commits/Paper-Moderation-System/commit/c55687a66ddeaff0037bb6b8d76ae0d8d2676f09), including its workflow from PR #1. The separate app has `User`, `Subject`, `Paper`, and `ModerationReport` models, first-examiner/lecturer/moderator subject assignments, PDF/Word files and a password-protected HOD handoff. Its `main` was older than `Dasika`. No changes were pushed to the separate repo, and no database connection to it was used.
- **Use existing accounts and module assignments.** The Results UI calls the paper setter the First Examiner (Module Lecturer), and the database uses `Module.activeLecturerId` with `SystemUser.isActiveLec`. The Results flag `isExamLec` is actually the **Second Examiner** flag (`Module.examLecturerId`), not the setter. For this integration, the First Examiner maps to the paper-setting lecturer, and the Second Examiner maps to the paper moderator. A dual-capability account can be a setter on one module and a moderator on another, but cannot review its own submission. HOD/Admin keep their existing duties; neither receives moderation access solely by being HOD/Admin.

## What this PR does

From **Lecturer Desk** or **Examiner Hub**, open **Paper Moderation**. For a module with two different eligible people assigned, the lecturer records a non-confidential paper reference and academic period. The moderator can request a revision with notes or approve; the lecturer can resubmit after a revision request. Both can see the paper's history as long as they are currently assigned. Approval ends this tracking workflow; it does **not** send anything to HOD, finalize an exam, change a blueprint, or release results. This first slice supports one record per module/academic year/semester; confirm the policy for repeat or supplementary sittings before expanding it.

The moderation tables and write path are separate from the marks ledger and `Module.stats`. Each status change records a versioned event with actor ID, action, note/reference, and timestamp. The API checks a server-signed, HTTP-only session issued at normal results login, current account capabilities and current module assignments. When enabled, it also checks the results endpoints that can change those permissions/assignments, and protects profile reads/edits so recovery addresses cannot be edited for another user. This is **not** a security retrofit for all legacy marks/results APIs. Use this as a **staging pilot with test data only**; review legacy API authorization, account/recovery data, login rate limiting and session revocation before production.

**Scope:** continue sharing exam documents through the existing approved private channel. Do not enter paper content, file links, passwords, or student data in references or notes. No file upload/download, Word/PDF reports, signatures, moderation-specific HOD finalisation, moderation account approvals, or historical data import is included. Neither repository's data is copied by merging this PR.

## Run the pilot

1. Use an isolated PostgreSQL database. Set the existing `DATABASE_URL` (app) and `DIRECT_URL` (Prisma CLI) to that database. Review migration history and take a backup before running against any database with data. For a fresh or correctly baselined database, run `npx prisma migrate deploy` and `npm run db:generate`. If an existing results database was provisioned with `db push`, have its schema verified and baseline the initial migration before applying the new one. Do **not** use this repo's `db:push` script for deployment (it passes `--accept-data-loss`).
2. Set `NEXT_PUBLIC_PAPER_MODERATION_ENABLED=true` before starting development or building the app. Set `PAPER_MODERATION_SESSION_SECRET` to at least 32 random characters (e.g. generate with `openssl rand -hex 32`; store it privately in deployment configuration). Production cookies require HTTPS. After enabling, anyone already signed in should sign out and back in to receive a server session. The moderation session expires after eight hours; users can sign in again without changing their account.
3. Assign an eligible First Examiner and Second Examiner to the same module through the existing consoles. Use two browser profiles to verify submit → request revision → resubmit → approve. Verify an unassigned account sees no module, and compare the unchanged results/marking data. Existing browser login validation has a domain mismatch with signup; use `@wyb.ac.lk` fixture accounts until the mismatch is addressed separately.
4. `npm test` runs the existing results suite plus moderation unit tests. To run the additional workflow test, set `MODERATION_TEST_DATABASE_URL` to a **disposable migrated test database** and run `npm test`. The test creates and removes its own fixtures. The check covers authorization, role changes, history, stale/concurrent actions, and unchanged marks. The starting results branch already has seven Prisma JSON TypeScript diagnostics; this PR adds none. The production build is not certified by this pilot.

## Disable or revert safely

- **Disable only:** unset or set `NEXT_PUBLIC_PAPER_MODERATION_ENABLED=false`, then rebuild/redeploy (or restart the dev server). The menu links disappear and the moderation endpoint returns 404. The moderation data and existing results data are retained. Nothing needs to be reset or deleted. If re-enabling after a rollback, configure a new session secret and sign in again.
- **Restore pre-integration code:** redeploy the starting SHA above, or revert this PR on `Dasika` (for a merge commit use `git revert -m 1 <merge_commit>`; for a squash merge revert the squash commit). Do not rewind or force-push the shared branch. Later changes, if any, are not included by redeploying the starting SHA.
- **Database:** code rollback does not undo a migration. The additive tables can remain. Their foreign key prevents deleting modules that still have moderation records, even with the feature off or pre-integration code redeployed. If full schema rollback or such a deletion is required, have a DBA back up/export the moderation data, plan a forward corrective migration and reconcile Prisma history; do not reset the database or restore an old backup over newer marks merely to turn off the pilot.
